## 一、启动与访问

### 1.1 当前部署形态

| 项 | 值 |
|---|---|
| 管理后台 | <http://127.0.0.1:59188> |
| 服务进程 | `runtime\bin\xianyu-server.exe` |
| 数据库 | `data\xianyu_data.db`（SQLite，零依赖） |
| 日志 | `logs\server.log`（JSON 结构化） |
| 管理员用户名 | `admin` |
| 管理员密码 | 部署时设置（不写在本文件里） |
| 监听地址 | `127.0.0.1:59188`（仅本机可访问，刻意如此） |

> 上游默认是 `-addr :59188`（监听**全部**网卡）。本部署固定用 `127.0.0.1`，
> 因为管理后台能完全操作你的闲鱼账号。

### 1.2 启动 / 停止 / 看状态

三种方式，效果一样：双击 `.bat`、用命令行、或装成 Windows 服务。

| 操作 | 双击 | 命令行（在仓库根目录） |
|---|---|---|
| 启动 | `启动.bat` / `start.bat` | `.\deploy\start.ps1` |
| 停止 | `停止.bat` / `stop.bat` | `.\deploy\stop.ps1` |
| 看状态 | `状态.bat` / `status.bat` | `.\deploy\status.ps1` |
| 打开后台 | `打开后台.bat` | — |
| 验证部署 | `验证部署.bat` / `verify.bat` | `.\deploy\verify.ps1 -Password '<你的密码>'` |
| 重新构建 | — | `.\deploy\build.ps1` |
| 装成服务 | `安装服务.bat` / `install-service.bat` | `.\deploy\install-service.ps1 -Mode install`（需管理员） |
| 重置管理员 | — | `.\deploy\reset-admin.ps1` |

关键参数（`deploy\start.ps1`）：

| 参数 | 默认 | 说明 |
|---|---|---|
| `-Port` | `59188` | 监听端口 |
| `-BindAddress` | `127.0.0.1` | 绑定地址；改 `0.0.0.0` 才能被别的机器访问（**不建议**） |
| `-Foreground` | 关 | 前台运行，启动报错直接打在屏幕上 |
| `-SkipBrowser` | 关 | 不启动 Chromium（浏览器相关能力不可用） |

`deploy\stop.ps1` 支持 `-Quiet`；`deploy\status.ps1` 支持 `-Json`；`deploy\verify.ps1` 支持 `-SkipBrowser` / `-SkipRestart` / `-Json`。

### 1.3 脚本实际用的是哪条命令行

`deploy\start.ps1` 最终会这样拉起服务（源码事实，参数值随 `-Port` / `-BindAddress` / `-SkipBrowser` 变化）：

```text
runtime\bin\xianyu-server.exe `
  -addr 127.0.0.1:59188 `
  -db <仓库根>\data\xianyu_data.db `
  -workdir <仓库根> `
  -playwright-driver-dir <仓库根>\runtime\playwright\playwright-driver `
  -playwright-browser-dir <仓库根>\runtime\playwright\playwright-browsers `
  -data-key-file <仓库根>\data\data.key
```

`deploy\install-service.ps1` 注册的 Windows 服务用**同一组参数**，只是额外加 `-service`。

这三件事值得记住：

- **`-data-key-file` 指向 `data\data.key`** —— 这就是本次部署里敏感数据的加密密钥文件（默认不存在时服务会自动生成）。
  它和 `data\xianyu_data.db` 必须成对备份（见 §10.3）。
- **`-workdir` 是仓库根** —— 数据与浏览器目录都相对它解析。
- 想手工排查时可以直接照抄上面的命令，但**先停掉已有服务**，否则两个实例会抢同一个 SQLite
  （表现为 `database is locked`）。

### 1.4 启动后的正常表现（用 `status.ps1` 核对）

服务健康时你会看到服务进程、运行时长、监听端口、健康检查、版本、数据库路径与大小、
Chromium 就绪状态、以及管理后台地址。健康接口可以直接问：

```powershell
Invoke-RestMethod http://127.0.0.1:59188/health
# {"status":"ok","database":"ok","version":"...","commit":"...","build_time":"..."}
```

`status` 为 `ok` 且 `database` 为 `ok` 才算正常；`database` 为 `unavailable` 时看第 12 章。

### 1.5 账号说明

- 用户名固定 `admin`（首次初始化时创建）。
- 密码是**你自己改过的那一个**。忘了就 `.\deploy\reset-admin.ps1`（会自动生成新密码并打印）。
- 修改后台登录凭据：**系统与AI → 修改登录凭据**（`POST /api/v1/session/password`、`POST /api/v1/admin/password`）。
- 本手册**不会**记录、推断或展示任何密码与凭据文件内容。

### 1.6 不要频繁重启

**有账号登录时，不要频繁重启本程序。** 每次重启都会向闲鱼申请登录凭证，达到某个频率即触发风控。
关掉浏览器窗口不影响服务运行 —— 不关机就不用停。

## 二、首次配置完整流程（从零到能自动发货）

按顺序做，每一步都别跳。**第 9 步之前务必用小额/测试订单验证。**

1. **登录后台** → <http://127.0.0.1:59188>，用 `admin` + 你的密码。
2. **确认系统时间与时区正确**（`TZ` / 宿主时区）。续期、擦亮时间、日志时间都依赖它。
3. **账号管理 → 扫码添加新账号** → 用手机闲鱼 App 扫码。
   - 触发人脸/安全验证时，按页面提示在官方流程里完成，**不要把验证链接转发给任何人**。
   - 等待账号状态变为**在线**，并立刻填**备注**（多账号时靠它区分）。
4. **确认账号处于启用状态**，且「自动发货」开关按你的业务需要打开（见第五章 5.3）。
5. **商品列表 → 同步商品**（选择账号）。已有商品必须同步到本地，规则才有东西可匹配。
6. **订单管理 → 一键同步订单**。看是否有部分失败，失败原因先记录。
7. **卡密库存 → 添加新卡密**，建立至少一个启用、有库存的卡密组；
   复制**卡密组 ID**（后面所有引用都用它）。
8. **（可选，但强烈建议）发货模板**：多条顺序消息 + 变量，见第七章。
9. **自动化规则 → 交易自动化 → 新建「付款后自动发货」**：
   选账号 → 选商品（多规格时逐个规格配）→ 绑定卡密组 → 保存并确认**规则启用**。
10. **先用测试商品验证**：用小额订单跑一遍，确认
    ①卡密内容已发给买家 ②库存正确扣减 ③自动化异常区没有待处理项。
11. `自动确认发货` **先关着**跑通几次；确认无误后再打开（见第五章 5.3）。
12. **配置消息回复**：关键词回复 / 账号默认回复 / AI 回复，见第六章。
13. **配置通知渠道并绑定到账号**，尤其是「需要人工处理」这一类事件，见第八章。
14. **账号自动任务**（可选）：账号管理 → 卡片上的「自动评价与每日擦亮」，先配文案和时间，再启用。
15. **正式开放前最后一遍**（对照 `app\docs\wiki\账号、库存与商品.zh-CN.md` 的「上线前检查」）：
    账号在线且启用 / 商品已同步且价格库存正确 / 卡密组启用且余量充足 /
    规则精确匹配商品与规格 / 通知可达 / 异常列表干净。

## 四、核心概念与数据流

### 4.1 一句话串起来

```
闲鱼账号 →（同步）→ 商品 → 买家下单 → 订单
                                    │
      卡密库存（文本/批量/图片/API）─┤
      发货模板（多条消息+变量）─────┤
                                    ▼
                         自动化规则（4 类触发 + 规格匹配）
                                    ▼
                        发送卡密/模板 →（可选）确认发货
                                    ▼
              消息回复链路：关键词 → AI → 默认回复
                                    ▼
                     通知渠道（按账号绑定 + 事件筛选）
```

### 4.2 每个环节干什么

- **账号**：一切的前提。账号必须**启用**且**在线**，否则该账号的自动化、自动评价、擦亮全都不执行。
  每个账号的会话、商品、订单、规则互相隔离。
- **商品**：本地只保存一份镜像（标题、价格、规格标记 `is_multi_spec` 等）。规则是按
  `账号 + 商品（+ 规格）` 匹配的，商品没同步就没有匹配对象。
- **订单**：定时同步 + WebSocket 实时事件共同维护。触发自动化的主力是**平台系统消息**，
  订单状态扫描只作为**丢失消息后的兜底**。
- **卡密库存**：自动发货的**交付内容载体**。一个卡密组 = 一份可交付内容；批量卡密组 = 一个可消耗的库存池。
  规则和批量铺货表格都通过**卡密组 ID** 引用它。
- **发货模板**：把「一次交付」表达成**多条顺序消息**，并支持变量替换。
  只能用在**付款后自动发货**和**评价后发送赠品**，不能用于拍下改价或求评价。
- **自动化规则**：把「触发条件 + 商品/规格匹配 + 动作链」绑定起来。共 4 类触发（见第五章）。
- **消息回复**：处理**买家普通消息**，链路优先级为 关键词回复 → AI 回复 → 默认回复。
- **通知**：**渠道 + 账号绑定 + 事件筛选**三者齐备才收得到。只建渠道不绑定账号 = 收不到。
- **敏感数据**：Cookie、密码、设备令牌、AI Key、SMTP 凭据、通知凭据都用
  `XIANYU_DATA_KEY`（本部署是 `data\data.key`）做 AES-256-GCM 加密。
  **密钥丢了 = 这些数据永久无法解密**（见第十章）。

### 4.3 交易自动化的两条驱动路径

| 路径 | 何时用 | 行为 |
|---|---|---|
| 主路径：WebSocket 系统消息 | 正常情况 | 付款/评价/系统卡片到达即触发对应规则 |
| 兜底路径：订单状态扫描 | 实时消息丢失、或订单在准备阶段就失败 | 每分钟扫一次待发货订单，补一次触发；**不会调用免拼接口**，不会重复发卡 |

兜底相关开关：`XIANYU_PENDING_SHIP_CATCHUP`（默认开启）。同一订单两次兜底之间**至少间隔 10 分钟**；
一旦订单已经产生过任意 `order_paid` 运行，就不再被兜底选中，改走异常区。

## 五、自动化规则怎么配

菜单：**自动化规则 → 交易自动化 → 新建自动化规则**。

### 5.1 四类触发条件（`trigger_type`）

| 触发条件 | 内部值 | 触发时机 | 标准流程 |
|---|---|---|---|
| **拍下未付款自动改价** | `order_created` | 收到「拍下未付款」系统卡片 | 匹配商品/规格 → 把订单改为**目标价格** → 可选发送提醒文本 |
| **付款后自动发货** | `order_paid` | 收到付款系统卡片 | 匹配商品/规格 → 发送卡密/模板 → 按账号开关决定是否确认发货 |
| **评价后发送赠品** | `buyer_reviewed` | 收到评价系统卡片 | 匹配商品/规格 → 发送赠品卡密 |
| **超时未评价求评价** | `review_missing_timeout` | 定时扫描「已发货未评价」订单 | 到达等待时间 → 发送求评价文案 |

各触发可用的动作类型（源码事实）：

| 触发 | 动作链 |
|---|---|
| 拍下改价 | `adjust_price`（目标价格，金额范围 0.01 ~ 1000000 元，最多两位小数） |
| 付款后发货 | `send_card` 或 `send_template` → `confirm_shipment` |
| 评价赠品 | `send_card` 或 `send_template` |
| 求评价 | `send_text` |

### 5.2 多规格 SKU 怎么配（最容易配错的地方）

规则里的「发货规格」条目（`variants`）字段是 `spec_name` / `spec_value` / `card_id` /
`delivery_count` / `enabled` / `delay_override` / `delay_seconds` / `delivery_mode` /
`delivery_template_id` / `template_bindings` / `custom_variables`。

要点：

1. **多规格商品必须为每个需要交付的规格组合建一条对应配置**。
2. 系统只执行**完整匹配整单 SKU 组合**的动作；**不会按部分规格或待获取金额猜测规则**。
3. 规则保存时，多规格规则的 `spec_name` / `spec_value` 才会被写入；
   非多规格规则这两个字段会被清空。
4. 单规格商品不填规格，直接选卡密组即可。
5. 商品列表里「关联发货规则 / 查看发货规则」可以跳到对应商品的规则 —— 规格商品**逐个规格确认**。

### 5.3 砍价与「待刀成」场景（不可变业务顺序）

砍价订单严格按三个阶段走，**顺序不能颠倒**：

| 阶段 | 收到的系统消息 | 必须做什么 |
|---|---|---|
| 1 | 「我已小刀，待刀成」 | **只**读账号的独立「自动免拼」开关；开关开才调用免拼接口。**此阶段严禁发卡、发模板、确认发货** |
| 2 | 「我已成功小刀，待发货」 | 才进入付款后自动发货规则，执行发卡或发货模板 |
| 3 | 发卡/模板成功后 | 才可按「自动确认发货」开关调用普通确认发货 |

四条可测试分支，别把「商品类型」和「免拼阶段」混成一个判断：

| 分支 | 行为 |
|---|---|
| 常规发货 | 付款卡片 → 取金额/数量/规格 → 匹配发卡/模板 → 发卡成功 → 按开关确认发货 |
| 多规格发货 | 付款卡片 → 取完整 SKU 组合 → **只**执行完整匹配该组合的动作 → 发卡成功 → 按开关确认发货 |
| 二人小刀·未开自动免拼 | 「待刀成」阶段不处理；收到「我已成功小刀，待发货」后走与常规发货相同的发卡+确认顺序 |
| 二人小刀·开了自动免拼 | 「待刀成」**只免拼一次**；必须等「我已成功小刀，待发货」后才发卡；发卡成功后才允许确认发货 |

**自动免拼开关关闭，不阻止已经到达「待发货」阶段的订单发卡。**
**确认发货不得因为订单是砍价订单而改调免拼接口。**

### 5.4 三个开关的正确用法（都在「账号管理 → 编辑账号」）

`AccountEditModal` 里是**三个互相独立**的开关，字段来自账号 schema：

| 开关 | 字段 | 作用 | 什么时候开 |
|---|---|---|---|
| **自动发货** | `auto_confirm` | 该账号是否参与付款后自动发货 | 做虚拟商品自动交付时开；不开则该账号不自动发货。**界面徽章「自动发货」反映的就是它** |
| **自动确认发货** | `auto_consign` | 发完卡密后自动调闲鱼「已发货」接口，订单才会变为已发货（**需同时开启上方「自动发货」**） | **首次配置建议先关**。慢充类业务建议关闭，避免触发买家自动收货倒计时 |
| **自动免拼** | `auto_bargain` | 只控制「待刀成」阶段的免拼 | 处理砍价订单时开；不替代自动发货或自动确认发货 |

容易踩的坑：

- 「自动确认发货」**不代表一定已经发送卡密**。完整自动发货还需要商品、规则、库存三者都正确。
- 关闭「自动确认发货」时，你仍能在后台看到发货记录，但**平台订单不会变成已发货**。
- 想只改平台状态不发内容？用订单管理的**手动发货 → 仅修改闲鱼发货状态**，不要用规则去凑。

### 5.5 账号级规则与「全部商品」兜底

- 规则不选商品时是**账号级规则**。付款发货场景下，账号级规则**只有在 `config_json` 里
  `allow_all_items` 为布尔 `true`** 时才被当作「商品缺少规则时的兜底」。
  界面上表现为必须勾选**「我确认此发货内容适用于该账号的全部商品」**；没勾选就不生效，也不作为兜底。
- 求评价规则的账号级用法不受这条确认约束。
- 规则有**优先级**字段（`priority`）与**启用**状态；搜索、按账号/触发类型/启用状态筛选在列表页。

### 5.6 求评价的时间参数（默认值与算法）

求评价配置存在 `config_json` 里，字段与默认值：

| 字段 | 默认 | 含义 |
|---|---|---|
| `after_shipped_hours` | `72` | 发货后多少小时开始检查 |
| `repeat_interval_hours` | `24` | 重复提醒间隔小时 |
| `max_attempts` | `1` | 最多提醒次数 |
| `max_lookback_hours` | 未显式配置时自动推导 | 「仅处理最近 N 小时内发货的订单」的回溯窗口 |

回溯窗口的口径（前后端一致）：**未显式配置时 = `after_shipped_hours + (max_attempts - 1) × repeat_interval_hours + 24` 小时**；
显式配置时取 `max(显式值, after_shipped_hours)`。

这条规则的实际意义：**规则停用一段时间后重新启用，不会给历史订单补发求评价消息。**

默认求评价文案：`亲，商品使用满意的话，麻烦给个评价，谢谢～`

### 5.7 异常与延迟任务

自动化规则页有**异常区**，列出可处理的自动化运行（`automation-issues`）和延迟任务
（`automation-pending-tasks`），可执行「处理/解决」。

处理原则：**先看订单、库存、聊天记录、失败原因，再决定处理方式**。
不确定是否已经发过内容时，**不要直接重试** —— 会重复发卡。
所有进入「需要人工处理」状态的路径都会发送独立类别的通知（见第八章）。

## 六、消息回复怎么配

买家**普通消息**的回复链路优先级：

```
① 关键词回复（命中即回复，最高优先）
② AI 回复（仅砍价 / 全场景客服）
③ 账号默认回复（最后的兜底）
```

上游文档还提到代码里保留了「外部 API 回复器」的扩展接口，若将来装配则其优先级高于关键词回复 ——
**当前生产运行时未装配该回复器**，所以实际生效的就是上面三级。

⚠️ 官方系统消息**不进入**这条链路（见 §6.4）。

### 6.1 关键词回复（`/app/rules` → 关键词回复页签）

- **入口**：选账号 → 新增规则 → 保存。
- **表达式**：一条规则可加**多个表达式**并共用同一条回复，**任一命中即触发**（OR 关系）。
  - 「包含匹配」下，**单个表达式**还可以用 `|`、中文逗号、英文逗号、顿号或换行分隔多个候选词。
  - 「正则表达式」模式下，`|` 是**正则分支**，**不做拆分**。
- **匹配模式**（`match_type`）：`contains`（包含匹配）或 `regexp`（正则表达式）。
  - 正则使用 **Go/RE2 语法并忽略大小写**；浏览器先校验一次，保存时服务端再按 Go/RE2 校验一次。
- **关联商品**（`item_ids`）：一条规则可关联多个已同步商品；**不选 = 账号级规则**。
- **回复内容**：文本（`reply_content`）或图片 URL（`image_url`）；回复类型字段为 `type`。

源文件里给出的输入提示（可直接照抄思路）：
- 包含匹配占位符：`例如：在吗 | 在不在 | 有人吗`
- 正则占位符：`正则表达式，例如：在吗|在不在`

对应接口：`GET /api/v1/reply-rules/{cid}`、`GET/POST/PUT/DELETE /api/v1/reply-rules/{cid}/typed`、
`DELETE /api/v1/reply-rules/{cid}/index/{index}`、`GET /api/v1/reply-rules/{cid}/items`。

### 6.2 账号默认回复（`/app/rules` → 账号默认回复页签）

- 只在**关键词未命中且 AI 未接管**时使用。
- 字段：`enabled`、`reply_content`、`reply_image_url`、`reply_once`。
  - `reply_once` = **同一会话只发送一次默认回复**，避免对同一个买家反复刷屏。
  - 启用默认回复时，**必须填写回复内容或图片 URL**，否则保存会被拒绝。
- 想对已经回复过的会话重新使用「只回复一次」：点**清空该账号默认回复记录**
  （`POST /api/v1/default-replies/{cid}/clear-records`）。
- **指定商品默认回复优先于账号默认回复**（接口 `GET /api/v1/default-replies/list` 与前端的按商品维度一致）。

对应接口：`GET /api/v1/default-replies`、`GET/PUT/DELETE /api/v1/default-replies/{cid}`、
`POST /api/v1/default-replies/{cid}/clear-records`。

### 6.3 AI 回复（系统与AI + 账号管理 → AI 设置）

**系统级**（系统与AI 页，仅管理员）：

1. 填 **OpenAI 兼容 API 地址**，填到**版本根路径**即可，例如
   `https://api.openai.com/v1`（源码里默认值来自 `DEFAULT_AI_API_URL`，当前为阿里云百炼兼容地址）。
   **不要填完整 `/chat/completions` 路径。**
2. 填 **API Key** → 点**读取模型**（`POST /api/v1/settings/ai-models`）。
   读不到模型列表时手动输入模型名。
3. **测试连接**（`POST /api/v1/settings/ai-test`）验证完整链路。
4. 保存系统设置。

**账号级**（账号管理 → 编辑/AI 设置，接口 `GET /api/v1/settings/ai-reply/{cookie_id}`）：

| 字段 | 说明 |
|---|---|
| 启用 AI 自动回复 | 按账号独立开关 |
| AI 模式（`ai_mode`） | `bargain_only`（仅砍价，默认）或 `full_service`（全场景客服） |
| 最大折扣比例（`max_discount_percent`） | 百分比，`0` 表示**不允许**按比例降价 |
| 最大折扣金额（`max_discount_amount`） | 元，`0` 表示**不允许**按金额降价 |
| 最大砍价轮次（`max_bargain_rounds`） | 界面范围 1–10，保守设置 |
| 自定义提示词（`custom_prompts`） | 仅砍价模式 = 自定义提示词；全场景模式 = **店铺客服规则** |

两种模式的区别（界面原文）：

- **仅砍价**：仅在识别到砍价意图时调用 AI，其他消息继续走关键词/默认回复。
- **全场景客服**：未命中关键词时，AI 会处理商品咨询、发货、售后和砍价消息。
  砍价流程之外仍**禁止承诺折扣、退款或赔偿**，并引导买家联系人工；运费/邮费不按砍价处理。

**商品级覆盖**（商品列表 → 商品卡片「AI 客服」，接口 `PUT /api/v1/items/{cookie_id}/{item_id}/ai-settings`）：

- `继承账号 / 强制启用 / 强制停用`（字段 `ai_override`）。
- 可填该商品**专属资料**（最多 12000 字），仅作事实参考，**不能覆盖店铺规则和价格限制**。

⚠️ 界面提示：**只有开启自动改价后，已发送给买家的有效报价才会用于真实订单改价。**
也就是说 AI 报出的价格若没有对应的「拍下未付款自动改价」规则，不会真的改单。

⚠️ 不要把 Cookie、密码、完整订单隐私或其他机密写进提示词。

### 6.4 官方系统消息不参与回复（重要）

以下消息**不会**进入关键词、默认回复或 AI 回复链，而是以居中**系统消息卡片**展示：

| 识别依据 | 含义 |
|---|---|
| `contentType=14` | 平台通知类消息 |
| `contentType=25` | 确认收货后的评价提醒 |
| `contentType=26` | 交易卡片 |
| 发送方用户 ID `1400` | 闲小蜜 |
| 内容「发来一条新消息」 | 官方通知占位内容 |
| 「快给ta一个评价吧～」/「快给ta一个评价吧~」 | 评价提醒的兼容摘要 |

因此：**不要把闲鱼官方系统消息配成买家关键词来触发自动回复。**

### 6.5 在线聊天页能做什么

- 顶部按账号分 Tab，每个账号有独立会话列表与消息状态。
- 会话列表按闲鱼会话最后消息时间倒序，显示联系人/头像/昵称/用户 ID/商品摘要/未读数。
- 进入会话优先读本地缓存，再从闲鱼历史消息接口补齐；底部可继续加载更早消息与更多联系人。
- 支持**文本、闲鱼文字表情、图片**发送。**当前不支持从后台发送视频**（界面不提供视频按钮）。
- 实时事件走后端 `GET /api/v1/chat/ws`；**刷新或重连后以历史接口和本地数据库为准**，
  不只依赖 WebSocket 存续期间收到的消息。
- 昵称/头像缺失时点会话列表刷新按钮；系统联系人闲小蜜使用平台头像和固定名称。
- 联系人分页返回的空会话壳**不会**导入列表（避免出现只有「暂无消息」的伪联系人）。

### 6.6 账号级自动任务（不属于订单规则）

入口：**账号管理 → 卡片上的「自动评价与每日擦亮」**（`GET /api/v1/account-tasks/{cid}`，
手动执行 `POST /api/v1/account-tasks/{cid}/run`，记录 `GET /api/v1/account-tasks/{cid}/runs`）。

| 任务 | 行为 |
|---|---|
| **自动评价** | 账号级开关 + 统一好评文案（**最多 500 字符**）；后台持续扫描待评价订单；每个订单按交易订单 ID **幂等**执行，处理过的不重复评价。**不是每日任务**，可点「立即评价」跑一次 |
| **每日自动擦亮** | 账号级开关；按**北京时间**判断执行时间；**每账号每天最多一次**；默认 `03:00`，可在 `HH:mm` 范围调整；界面显示最近完成时间、发现数、成功数、失败数、跳过数 |

注意：**账号停用或暂停时不会执行**。部分商品失败时会记录原因并进入可重试状态 ——
不要只看按钮返回就认为全部成功，要看本次执行结果。
（上游文档提到擦亮按每页 20 条、最多 20 页读取商品，属实现细节，以上游版本为准。）

## 七、卡密与发货模板

### 7.1 四种卡密类型（`type` 枚举，来自 openapi 契约）

| 类型值 | 界面名称 | 内容字段 | 适用场景 | 取用行为 |
|---|---|---|---|---|
| `text` | 文本 | `text_content` | 固定说明、网盘链接 + 提取码、固定文案 | 每次都发**相同内容**，不消耗库存 |
| `data` | 批量卡密（编辑页叫「批量库存」） | `data_content` | 兑换码、序列号、账号密码 | **每行一条**，发货时**逐条消耗**，卖一条少一条 |
| `image` | 图片 | `image_url` | 交付图片（二维码、截图等） | 填写**可访问的图片 URL**，发货时临时发送 |
| `api` | API（编辑页叫「API 接口」） | `api_config` | 由你自己的发码系统按订单实时取码 | 调用外部接口，**返回什么就发给买家** |

通用字段：`name`、`description`、`enabled`、`delay_seconds`（延时发货，**0–3600 秒，0 = 立即**）、
`is_multi_spec`、`spec_name`、`spec_value`。

**卡密组 ID 是自动化的关键**：规则里绑卡密用它，批量铺货表格里的「付款发货内容 / 评价赠品内容」也用它。

### 7.2 批量卡密的库存追加与覆盖保护

- 新建 `data` 卡密组时在内容框逐行录入。
- 已有 `data` 组可以**批量导入**追加（`POST /api/v1/cards/{card_id}/append-data`），也可以走
  `POST /api/v1/cards/batch` 用表格批量创建。
- **不要重复导入同一批卡密。** 导入后检查成功数量与失败行。
- 编辑 `data` 库存时有**乐观锁**保护：提交时如果当前库存已经和打开弹窗时看到的不一致，服务端返回 **409**，
  不会静默覆盖（契约字段 `expected_data_content`）。

### 7.3 发完自动停

`data`（批量卡密）类型是**消耗型库存**：库存取完即无法再发（**发完自动停**）。
所以它必须配合：

1. 上架前的**库存余量检查**（仪表盘的库存余量、卡密库存列表的余量）。
2. 低于安全线就**先补货**，不要依赖人工事后补救。
3. 库存不足时**不要假设发货已完成** —— 去看自动化异常区。

### 7.4 API 卡密（能力最强、坑也最多）

**请求构建**：可粘贴 **cURL 命令**自动填充请求；请求方法 GET/POST；可配超时、请求头、查询参数、请求正文。

**可用变量**（只替换**请求头、查询参数、请求正文的值**，**不替换 URL，也不替换请求头名称**）：

```
{order_id} {item_id} {buyer_id} {chat_id} {account_id} {cookie_id}
{spec_name} {spec_value} {quantity} {order_quantity}
{amount} {order_amount} {item_detail} {trigger_type} {timestamp}
{delivery_unit_index} {delivery_total_count} {idempotency_key}
```

- GET 把参数放进 query；POST 按所选 Content-Type 发送正文（默认 JSON）。

**响应提取**：响应路径可写 `data.card.code` 或 `data.cards[0].code`；
**留空时**按 `data` → `content` → `card` 顺序提取。

**幂等重试**：启用后必须把 `{idempotency_key}` 写进**真正会发送的载荷**：

| 方法 | 可写位置 |
|---|---|
| GET | 请求头 **或** 查询参数 |
| POST | **只能**写请求正文（正文为空时系统会把参数当作正文发送） |

不满足条件时**保存会被拒绝**；历史配置会被标记为不可用并要求修正，实际发货也不会执行缺少幂等键的重试。
重试上限 **3 次**，只重试**网络错误、超时、408、429、5xx**。

**安全边界（唯一有文档记录的例外）**：
请求头、参数、正文整体加密保存；卡密列表/详情/规则接口**只返回是否已配置，不回显模板明文**。
仅当所属用户打开已保存的 API 卡密编辑时才通过 `GET /api/v1/cards/{card_id}/api-editor` 读取，
该接口要求登录 + 卡密归属 + `type=api` 校验，响应 `Cache-Control: no-store`，
密钥输入框默认遮罩，关闭弹窗或切换卡密后草稿即清除。

**其他**：已保存的卡密可直接**测试**，无需重填密钥（`POST /api/v1/cards/test-api`）。
先用**无敏感测试数据**确认响应格式，再启用正式自动化。

### 7.5 发货模板

**创建**：发货模板 → 新建 → 填名称 → 勾选是否启用 → 输入**一条或多条消息**（按页面顺序分别发送）
→ 至少保留一条消息 → 保存。

**可用变量**（源码与 Wiki 原文；直接写变量名，不加 `delivery.` 前缀）：

| 变量 | 含义 |
|---|---|
| `{{order_id}}` | 订单号 |
| `{{item_id}}` | 商品 ID |
| `{{item_title}}` | 商品标题 |
| `{{buyer_id}}` | 买家 ID |
| `{{buyer_nickname}}` | 买家昵称 |
| `{{card_name}}` | 规则绑定的卡密库存名称 |
| `{{cards.<变量名>}}` | 卡密内容，例如 `{{cards.main}}` |
| `{{custom.<变量名>}}` | 自动化规则中填写的自定义文字 |

**变量名规则**：只能使用**英文字母、数字、下划线或短横线**；
**不允许空格、中文变量名或未闭合的大括号**。保存时系统会校验拼写。

**示例模板**：

```text
感谢购买！
订单：{{order_id}}
主卡：{{cards.main}}
备注：{{custom.remark}}
```

**在规则中使用**：自动化规则 → 付款后自动发货 / 评价后发送赠品 → 发货方式选「发货模板」
→ 为模板里**每个 `cards` 变量绑定卡密库存** → 为每个 `custom` 变量填文字 → 保存并启用。

**约束**：

- 发货模板**只**用于「付款后自动发货」和「评价后发送赠品」，**不能**用于拍下改价或求评价。
- 仍被规则引用的模板**不能删除**；先改规则再删除。
- 模板声明的卡密变量与规则里的绑定必须**一一对应**，否则校验不通过。
- 模板执行器支持的卡密类型是**启用的文本、批量或已就绪的 API** 卡密 ——
  **图片卡券不支持嵌入文本模板**。（本点为源码事实，上游 Wiki 未展开，以你实际界面下拉可选为准。）

### 7.6 库存与交付相关的其他开关

- 规则动作里的「**每件发送数量**」（`delivery_count`）会**乘以订单购买数量**。
  按购买数量发货时，**不要把每单总量误填为每件数量**。
- 「延迟覆盖」（`delay_override` + `delay_seconds`）：打开后覆盖卡密组的默认延时；
  否则使用卡密组的 `delay_seconds`。
- 修改延时**只影响后续发货**，已经发送的内容不会改变。

## 八、通知渠道配置

菜单：**通知设置**。渠道类型共 **7 种**（源码 `NotificationChannelType` 枚举）：
`bark`、`dingtalk`、`feishu`、`wechat`（企业微信）、`telegram`、`email`、`webhook`。

### 8.1 逐渠道必填项

| 渠道 | 内部值 | 必填字段 | 可选字段 | 获取方式（源码内置指引） |
|---|---|---|---|---|
| **Bark** | `bark` | `server_url`（默认 `https://api.day.app`）、`device_key` | `title`、`sound`、`group` | 装 Bark App → 首页有一条测试 URL `https://api.day.app/<key>/...` → **路径里的 `<key>` 就是 Device Key**。自建服务端则填自建域名 |
| **钉钉机器人** | `dingtalk` | `webhook_url` | `secret`（加签密钥，`SEC` 开头） | 群设置 → 机器人 → 添加「自定义机器人」→ 安全设置勾选**加签** → 完成页同时给 Webhook 和 Secret |
| **飞书机器人** | `feishu` | `webhook_url` | `secret`（签名校验密钥，`sec-` 开头） | 群 → 更多 → 设置 → 群机器人 → 自定义机器人 → 安全设置选**签名校验**。**频率限制：单机器人 100 次/分钟** |
| **企业微信机器人** | `wechat` | `webhook_url` | 无 | 内部群 → … → 群设置 → 群机器人（新版可能叫「消息推送」）→ 自定义机器人。**URL 里的 key 就是唯一凭证**。**频率限制 20 条/分钟** |
| **Telegram** | `telegram` | `bot_token`、`chat_id` | 无 | @BotFather 发 `/newbot` 拿 Bot Token → 把 Bot 拉进群或私聊发一条 → 访问 `https://api.telegram.org/bot<你的Token>/getUpdates` → 找 `"chat":{"id":xxx}`（群为负数，私聊为正数）。群聊需先把 Bot 设为管理员 |
| **邮件** | `email` | `to_email`（收件邮箱） | 由 SMTP 决定 | **默认完整继承系统 SMTP**；只有确实需要另一套发件服务时才开「使用独立 SMTP」并填完整配置（`use_custom_smtp`） |
| **自定义 Webhook** | `webhook` | `webhook_url` | 无 | 系统会 **POST** 该 URL，`Content-Type: application/json`，请求体固定为 `{"message":"...","timestamp":"2026-07-05 12:00:00","source":"xianyu-auto-reply"}`。**Server酱 / PushPlus 等格式不兼容**，需中间脚本转发或改用专用渠道 |

字段名说明：上述 `server_url`、`device_key`、`webhook_url`、`secret`、`bot_token`、`chat_id`、`to_email`
都是前端源码里的实际配置键。

### 8.2 系统 SMTP（只有邮件渠道需要）

- 位于「通知设置」页的**SMTP 邮件配置**（系统级，供邮件渠道复用）。
- 认证优先 `PLAIN`；服务器仅提供 `LOGIN` 时自动用 `LOGIN`。
- **`587` 端口使用 STARTTLS，不要同时启用 SSL/TLS 直连。**
- **SendCloud**：SMTP 登录账号填 `API_USER`，密码填对应 `API_KEY`，**发件邮箱地址单独填写**。
- 邮件渠道有「保留已有 SMTP」模式：只想改收件地址时不会读取或替换已有发信凭据
  （契约字段 `email_recipient`）。

### 8.3 事件订阅

新建渠道时选择接收事件；**不选择 = 接收全部**。可订阅的事件（源码 `notificationEvents`）：

| 事件值 | 界面名称 | 含义 |
|---|---|---|
| `account_offline` | 掉线通知 | 账号过期、断线或登录态失效 |
| `account_recovered` | 恢复通知 | 自动恢复成功并重新在线 |
| `account_disabled` | 禁用通知 | 连续失败、账密错误等导致账号停用 |
| `security_verification` | 风控验证 | 滑块、人脸、扫码验证等安全校验 |
| `automation_order_created` | 拍下改价 | 自动改价任务的成功或失败结果 |
| `automation_order_paid` | 付款发货 | 自动发货任务的成功或失败结果 |
| `automation_buyer_reviewed` | 评价赠品 | 评价赠品任务的成功或失败结果 |
| `automation_review_missing_timeout` | 求评价 | 求评价任务的成功或失败结果 |
| `manual_delivery_result` | 手动发货结果 | 人工发货或确认发货的结果 |
| `manual_intervention_required` | **需要人工处理** | 自动化因结果不确定、状态缺失或无法安全续跑而停止，需要你检查订单 |
| `token_renewal` | 续期通知 | Cookie/token 续期和自动恢复过程 |
| `system_error` | 系统错误 | 后台任务或系统级异常 |

### 8.4 三步才生效（最常见的「为什么没收到通知」）

```
① 建渠道 → 点「测试通知」确认渠道本身可用（POST /api/v1/notifications/channels/{channel_id}/test）
② 账号管理 → 编辑账号 → 通知渠道绑定 → 勾选渠道并保存
③ 在该渠道的事件里勾选对应类别（自动发货要勾「付款发货」）
```

**只创建渠道而没有绑定账号，不会收到该账号的通知。**
测试通知**只验证渠道配置本身**；自动化结果通知还要求绑定 + 事件筛选都正确。

通知在任务进入**完成、失败或需要人工核对**状态时触发。
排查顺序：先测试通知 → 再核对事件筛选与账号绑定 → 仍未到就看 `logs\server.log` 里
自动化通知的触发、写入队列和发送结果记录。

### 8.5 通知相关配置的安全提醒

Webhook URL、群机器人令牌、Bot Token、Device Key **等同于密码**：
不要贴进截图、Issue、聊天记录；更换令牌后立即更新渠道并重测。
通知凭据随 `XIANYU_DATA_KEY` 加密，**换密钥会导致旧凭据无法解密**。

## 十一、风控与安全红线

### 11.1 绝对不能改的参数（改了就是拿账号冒险）

| 红线 | 为什么 |
|---|---|
| **`internal\xianyu\mtop\pacer.go` 的请求节流**（同账号请求起点间隔 ≥ 2 秒 + 随机抖动；后台批量任务 ≥ 5 秒） | **风控一旦触发短期内无法恢复**，定时冷却或熔断只是事后补救，**唯一有效的做法是从源头保证请求频率低**。上游有测试守护「生产代码不得绕开节流」 |
| 订单详情协调器（`adapter/order_detail_coordinator.go`）的既有更严格间隔 | 不得与账号级节流器互相替代而放宽 |

## 十二、常见问题

### 12.1 打不开管理后台

1. `.\deploy\status.ps1` 看服务是否在跑；
2. 没跑 → `.\deploy\start.ps1`；
3. 在跑但打不开 → `Get-Content .\logs\server.log -Tail 100`；
4. 端口被占（上次没停干净）→ `.\deploy\stop.ps1`，或换 `-Port`。

### 12.2 健康检查 `database: unavailable`

数据库文件损坏或无权限。看日志定位；必要时**从备份恢复** `data\xianyu_data.db` 与
`data\data.key`（**两个必须配对**）。**不要通过删库来「修复」。**
`database is locked` 则通常是两个实例共用同一个 SQLite —— 确认只有一个 `xianyu-server` 进程。

### 12.3 启动后立刻退出，日志停在「系统尚未初始化」

找不到 Chromium 且没加 `-no-browser`。检查 Playwright 路径，或确认
`.\deploy\bootstrap.ps1` 装过 Chromium（约 700 MB，在 `runtime\playwright\`）。

```powershell
.\deploy\verify.ps1 -SkipRestart   # 看 G 段「服务内 Playwright Chromium 已就绪」
.\deploy\bootstrap.ps1 -Force      # 丢了就重装（会重新下载约 700 MB）
```

### 12.4 停止服务要等十几秒

**属已知行为，不是故障。** 上游当前版本**不消费「停止标记」文件**，脚本按
「写标记 → 等约 15 秒 → 关闭窗口 → 强杀」逐级退让；数据由服务自身的写入事务保证。

### 12.5 服务起来了，脚本却像卡死

**不要把 `start.ps1` 的输出接进管道**（`& .\deploy\start.ps1 2>&1 | Out-String`、CI 步骤包装、某些 IDE 任务）。
长驻服务继承了调用方的 stdout/stderr 句柄，调用方永远等不到 EOF。
要看启动细节用 `-Foreground`，或直接读 `logs\server.log`。

### 12.6 账号掉线或需要安全验证

- 在**账号管理**看状态和续期日志；点**重新登录**扫码。
- 根据页面提示在闲鱼 App 完成人脸/安全验证。
- 检查服务器时间、时区和外网连接是否正常。
- **不要同时在多个实例里运行同一个闲鱼账号**（凭证会互相覆盖）。
- 若一直要求安全验证：清除该账号登录凭证、停用账号 → 登录闲鱼官方 Web 版打开消息页 →
  人工通过风控后等一会儿 → 再回来尝试登录。
- 状态显示「运行状态冲突」= 数据库已停用但旧运行实例仍存活，**不要当作已停用**，
  等待或重试停用并检查服务日志。
- 上游生产登录入口是**扫码**；`/api/v1/password-login*` 系列接口仍存在于契约中，
  **是否为当前推荐流程以上游文档为准，未在本次核对**。

### 12.7 没有自动发货

按顺序核对（这是上游给出的排查顺序）：

1. 订单所属**账号**是否正确、账号是否**启用且在线**；
2. **商品/规格**是否与规则精确匹配（多规格要逐个规格确认）；
3. 规则是否**启用**；
4. **卡密库存**是否启用且有余额（`data` 型是否已发完）；
5. 账号的**「自动发货」开关**（`auto_confirm`）是否打开；
6. 看**自动化异常区**有没有待处理项；
7. **先确认是否已经实际发送过内容** —— 不确定就别重试，避免重复发卡。

补充：付款自动发货只由平台付款系统消息触发；若该消息丢失，兜底调度器每分钟扫一次并在
本地最后一次观测到待发货状态至少 2 分钟后补一次触发。同一订单两次兜底至少间隔 10 分钟。
关掉了 `XIANYU_PENDING_SHIP_CATCHUP` 就等于关掉了这条兜底。

**手动补发**：订单管理 → 找到订单 → **手动发货**，选
「仅修改闲鱼发货状态」（只改平台状态，不发卡）或「完整发货（匹配卡券并发送）」。
**不确定是否已发过卡密时不要选完整发货。**

### 12.8 砍价订单没发卡

砍价订单必须等**「我已成功小刀，待发货」**卡片到达后才发卡。
如果一直没到，检查：账号「自动免拼」是否打开（未开则「待刀成」阶段系统不处理）、
免拼是否成功、是否已进入异常区。

### 12.9 求评价一直没发

- 检查规则是否启用、`after_shipped_hours` 是否还没到；
- 检查「最近 N 小时」回溯窗口 —— **发货时间早于窗口的订单不会被求评价**
  （规则停用一段时间后重新启用，不会给历史订单补发）；
- 检查是否已达 `max_attempts` 上限。

### 12.10 AI 没回复

1. 系统与AI 里的 **API 地址、Key、模型**是否可用（点「测试连接」）；
2. 该账号 **AI 是否已启用**；
3. 该商品是否被**强制停用** AI（`ai_override`）；
4. 消息是否符合当前模式 —— **「仅砍价」模式下必须是砍价消息**；
5. AI 未启用 / 未配 Key / 消息不适用 / 无可用结果 / 调用失败时，都会继续尝试**默认回复** ——
   所以「AI 没回但默认回复回了」是正常链路，不是故障。

### 12.11 通知收不到

见 §8.4 的三步检查：测试通知 → 账号绑定 → 事件筛选。
自动发货要勾**「付款发货」**；邮件还要检查系统 SMTP。
仍未收到就看 `logs\server.log` 里的通知触发、入队和发送结果记录。

### 12.12 库存不够了

`data`（批量卡密）是消耗型：**发完自动停**。
低于安全线先去**卡密库存 → 批量导入**补货，再继续投放商品。
不要把「人工事后补发」当成常规手段。编辑批量库存时注意 409（库存快照不一致）提示，重新读取后再提交。

### 12.13 双击 `.bat` 报「少花括号」且中文乱码

那是**脚本文件编码问题**（`.ps1` 少了 UTF-8 BOM，Windows PowerShell 5.1 按 GBK 解码把中文串撕裂），
不是你的操作错了。一分钟判定：

```powershell
.\tests\test_scripts.ps1        # 检查器会直接点名「缺少 BOM」
```

### 12.14 上游冒烟测试在 Windows 上必失败

```powershell
cd app
go run ./tools/smoke -bin ..\runtime\bin\xianyu-server.exe
# 冒烟失败: 发送终止信号: not supported by windows
```

**这是上游工具的平台限制**（用 `syscall.SIGTERM`，Windows 不支持 POSIX 信号），
功能检查其实全部通过，失败点只在最后一步「优雅终止」。
**用 `.\deploy\verify.ps1` 代替它。**

### 12.15 想换数据库

`DATABASE_URL` 优先级最高（`sqlite://` / `mysql://` / `postgres://`）。
MySQL 会强制补齐 `multiStatements=true` 和 `clientFoundRows=true`。
**切库前先备份当前库**；迁移在启动时自动执行；迁移不回滚。

### 12.16 改了前端看不到效果

```powershell
.\deploy\build.ps1     # 先停服务 → 构建前端 + Go → 自动启回来
```

浏览器硬刷新不够（前端编译进二进制）。只想重建 Go：`-SkipFrontend`。

| `LOG_FORMAT` | `json` | 日志格式 | 改成非 JSON 会破坏 `verify.ps1` 的日志断言 |
| `PLAYWRIGHT_DRIVER_PATH` | 空（用命令行参数） | Playwright driver 目录 | 本部署由 `start.ps1` 用 `-playwright-driver-dir` 显式传入，无需设环境变量 |
| `PLAYWRIGHT_BROWSERS_PATH` | 空（同上） | Chromium 运行时目录 | 同上，用 `-playwright-browser-dir` |
| `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH` | 空 | 指定 Chromium 可执行文件 | 只有在用系统自带 Chromium 时才需要 |
| `PLAYWRIGHT_NODEJS_PATH` | 空 | 指定 driver 用的 Node | 同上 |
| `PLAYWRIGHT_SKIP_BROWSER_DOWNLOAD` | 空 | 1 时跳过浏览器下载 | 上游打包/CI 用 |
| `PLAYWRIGHT_BROWSER_INSTALLER` | 空 | 指定浏览器安装器 | 上游打包用 |
| `BROWSER_HEADLESS` | 空（跟随程序默认） | `true` 时浏览器流程强制无头 | 服务器无桌面时设 `true`；本机有桌面时留空即可 |
| `CAPTCHA_BROWSER_PROXY` | 空 | 滑块/验证码浏览器走代理（**无凭证**的 `http(s)`/`socks`） | 只在特定网络环境需要；带账号密码的代理会被拒绝 |
| `XIANYU_DATA_KEY` | 空（改用 `-data-key-file`） | 敏感字段加密密钥 | 本部署用 `data\data.key` 文件，**不要**同时再设这个变量 |
| `XIANYU_UPLOAD_DIR` | 空（数据目录下 `uploads`） | 上传目录 | 改了要同步备份策略 |
| `XIANYU_ADMIN_PASSWORD` | 空 | 首次初始化管理员密码（Docker/非交互场景） | 本部署走 `-init-admin`，不用它 |
