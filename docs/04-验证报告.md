### 两点值得说明

**C 段的「静态资源真实命中」不是走过场。**
静态资源挂在 `/static/assets/` 下。如果按 `/assets/xxx` 请求，会落进 SPA 深链回退，
服务返回 **index.html 且状态码 200** —— 只看状态码会误判成"通过"。
所以这一项额外校验「返回的不是 `index.html`」。

**G 段的判据是「React 真的挂载了」。**
只看 HTTP 200 无法证明前端能跑（服务端返回的是静态 HTML 骨架）。
这里用真实 Chromium 渲染，检查 DOM 里 React 挂载点非空 + 出现界面文案 + 引用了静态资源。

## 五、上游冒烟测试（交叉验证）

```powershell
> cd app
> go run ./tools/smoke -bin ..\runtime\bin\xianyu-server.exe
冒烟失败: 发送终止信号: not supported by windows
exit status 1
```

**表面失败，实际功能检查全部通过。** 证据：

服务日志（冒烟器自起的临时实例）：

```
{"msg":"goose: successfully migrated database to version: 54"}
{"msg":"数据库已就绪","dialect":"<redacted>"}
{"msg":"系统尚未初始化，请先运行本二进制的 -init-admin 初始化管理员"}
{"msg":"playwright chromium 就绪"}
{"msg":"HTTP 服务启动","addr":"127.0.0.1:51228"}
```

失败点是 `tools/smoke/process.go:86`：

```go
if err := p.cmd.Process.Signal(syscall.SIGTERM); err != nil {
    return fmt.Errorf("发送终止信号: %w", err)
}
```

`syscall.SIGTERM` 在 Windows 上返回 `not supported`，上游没有 Windows 专用实现。
所以 `make smoke` 在 Windows 上**必然失败**，与部署正确性无关。

> 第一次跑的时候还出现了「等待服务就绪: 1m30s 内健康检查未通过」。
> 原因是冒烟器只传 `-db/-addr/-workdir/-data-key-file`，**不传 Playwright 路径**，
> 服务找不到 Chromium 就退出了。加上 `PLAYWRIGHT_DRIVER_PATH` /
> `PLAYWRIGHT_BROWSERS_PATH` 环境变量后，启动时间从「90 秒超时」降到 **1.3 秒**。

## 六、验证过程中修正的 5 个自身缺陷

验证脚本第一版报了不少「失败」，排查后发现**是我自己的检查写错了**。
列在这里，因为它们同时也是使用这套系统时容易误判的地方。

| # | 现象 | 真实原因 | 修正 |
|---|---|---|---|
| 1 | `静态资源 /assets/index-xxx.js → HTTP 200，1204 字节` 却判为通过 | 路径漏了 `/static` 前缀 → 落进 SPA 回退返回 index.html，状态码仍是 200 | 按 index.html 里**真实引用**的路径请求，并额外断言「返回的不是 index.html」 |
| 2 | `核心接口 卡密列表 FAIL`（实际返回 `[]`） | 用 `$null -ne $r.Json` 判断，空数组在 PowerShell 比较语义下被当成空 | 改为「HTTP 200 且响应体是合法 JSON」，不依赖对象非空 |
| 3 | `/api/v1/rules`、`/api/v1/dashboard` → 404 | 端点名是**我猜的**。真实路径是 `/api/v1/automation-rules`、`/api/v1/analytics/dashboard` | 从权威契约 `api/openapi.yaml` 取（158 个端点），再实测筛出 25 个可用的只读接口 |
| 4 | `/api/v1/chat/sessions` → 403 | 该路径**只有 DELETE 方法**，我当 GET 用了 | 用实测通过的端点，不用推测 |
| 5 | `数据库已完成管理员初始化 FAIL` | `/api/v1/session` 响应是**扁平**的 `{"initialized":true,...}`，我当成 `{"data":{"initialized":...}}` | 按真实响应结构解析（并做属性存在性检查，StrictMode 下访问不存在属性会抛错） |

还有三个**脚本实现**层面的坑：

| # | 现象 | 原因 |
|---|---|---|
| 6 | `不是有效的 Win32 应用程序` | Windows 上 `npm` 在 PATH 里是 `npm.ps1`，`Start-Process` 无法执行 `.ps1`。必须解析到同名的 `.cmd` |
| 7 | `flag provided but not defined: -w` | `Start-Process -ArgumentList` 把数组**用空格拼接且不加引号**，`-ldflags "-s -w ..."` 被拆成独立参数。必须自己按 Windows 命令行规则加引号 |
| 8 | Chromium 卡住 10 分钟不返回 | `Start-Process -Wait` 等的是**整个进程树**，Chromium 会留后台子进程。必须设超时 + `taskkill /T /F` |
