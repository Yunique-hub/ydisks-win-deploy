## 一、项目概览

| 项 | 值 |
|---|---|
| 名称 | Ydisks 闲鱼助手（Ydisks Xianyu Helper） |
| 定位 | 面向闲鱼卖家的**自托管**多账号自动化管理系统 |
| 技术栈 | **Go 1.26**（后端）+ **React 19 / Vite / TypeScript**（前端） |

### 关键设计判断

**1. `internal/composition` 是唯一生产组合根。**
所有依赖装配集中在一处，`cmd/server/main.go` 只做「解析配置 → 装配 → 启动 → 等信号」。
这让依赖关系可静态检查（仓库里有 `tools/architecturecheck` 门禁）。

**2. 前端产物用 `//go:embed` 嵌进二进制。**
带来两个后果：
- 部署时只需要**一个可执行文件**，没有前后端目录分离问题
- **前端改了必须重新构建 + 重启服务**，浏览器硬刷新不会替换运行中进程已加载的资源
  （上游 README 明确写了这一点）

**3. 数据库三方言并行维护。**
54 条迁移 × 3 个方言目录，编号与最终 schema 必须对齐。
代价是维护成本高，好处是**本地用 SQLite 零依赖，生产可换 Postgres**。

**4. Chromium 与 Go 二进制分离。**
Go 二进制 25.1 MB；Chromium 运行时 689 MB。分开分发让轻量场景（不需要浏览器功能）
可以只装二进制 —— 但代价是部署时必须显式处理浏览器路径（见下文「部署的三个坑」）。

**5. 多数据库连接协议：**
```
DATABASE_URL > -db-url > -db
# SQLite（默认，零依赖）
-db data/xianyu_data.db
# MySQL
mysql://user:pass@tcp(host:3306)/db?multiStatements=true&clientFoundRows=true
# PostgreSQL
postgres://user:pass@host:5432/db?sslmode=disable
```
MySQL 连接串里的 `multiStatements` 与 `clientFoundRows` 由程序**强制补齐**，
不允许使用者漏配。

### 值得单独说的业务约束（写在 AGENTS.md 里的「不可变规则」）

**砍价订单的严格顺序**（违反会导致资损）：

```
1. 收到「我已小刀，待刀成」 → 只读「自动免拼」开关，开启才调免拼接口
   ⚠ 此阶段严禁发卡、发发货模板、确认发货
2. 收到「我已成功小刀，待发货」 → 才进入发货规则
3. 发卡/发货模板成功 → 才按「自动确认发货」开关调确认发货接口
```

**MTOP 请求频率约束**（防封号）：

- 同账号请求起点间隔 **≥2 秒** + 随机抖动；后台批量任务 **≥5 秒**
- 禁止「列表 × 每项一次请求」的扇出
- 遇风控（`RGV587`）必须**立即终止本批次**，不得靠冷却后自动重放
- 生产代码只能通过 `mtop.NewClient()` 拿客户端，禁止构造字面量绕开节流
  （有 `TestProductionNeverInjectsHTTPClient` 守护）

> 这两条是这个项目里**最有价值的知识沉淀** —— 它们是从真实封号/资损事故里总结出来的。

## 七、风险与注意事项

### 7.1 部署层（本次实际遇到的）

| # | 坑 | 影响 |
|---|---|---|
| 1 | `npm` 在 Windows 上是 `npm.ps1`，`Start-Process` 无法执行 | 构建脚本必须解析到 `npm.cmd` |
| 2 | `Start-Process -ArgumentList` 用空格拼参数且不加引号 | `-ldflags "-s -w"` 被拆开，`go build` 报 `flag provided but not defined: -w` |
| 3 | 运行中的 exe 无法被覆盖 | 重建前必须停服务，否则留下 `.exe~` 垃圾且产物是旧的 |
| 4 | 版本变量在 `xianyu-go/internal/version` 而非 `main` | 写成 `-X main.commit` 静默无效，版本永远显示 `dev` |
| 5 | 冒烟工具只传 `-db/-addr/-workdir`，不传 Playwright 路径 | 服务找不到 Chromium 就退出 → 冒烟超时。需用 `PLAYWRIGHT_DRIVER_PATH` / `PLAYWRIGHT_BROWSERS_PATH` 环境变量传入 |
| 6 | 上游冒烟工具在 Windows 上最后一步失败 | `process.go:86` 用 `syscall.SIGTERM`，Windows 不支持。**功能检查全过**，只是优雅终止步骤报错 |

### 7.2 安全层（部署者必须处理）

| # | 风险 | 处理 |
|---|---|---|
| 1 | 管理端口默认可能监听全部接口 | 本部署固定绑 `127.0.0.1`；对外暴露需自行加反向代理 + TLS |
| 2 | 首次网页初始化无预共享密钥 | **能访问该端口的首个客户端就能创建管理员**。本部署改为 `-init-admin` 预初始化，规避这个窗口 |
| 3 | `XIANYU_DATA_KEY` 决定敏感字段加解密 | 丢失后**已加密的凭证无法恢复**，必须备份 `data/data.key` |
| 4 | 账号凭证托管在本地数据库 | 数据库文件 + 密钥文件等价于账号控制权，按凭证级别保护 |
| 5 | 项目会与闲鱼平台交互 | 必须遵守平台规则；项目自带 MTOP 节流约束，**不要为了提速去放宽它** |

### 7.3 使用层

- 本项目是**自动化工具**，不是绕过平台风控的工具。
  内置的请求节流、滑块处理、登录续期都是为了让正常使用不被误判。
- 用真实账号跑自动化前，**先用小号验证业务规则**（上游 README 也这么建议）。
- 交付类业务（卡密、网盘链接）的资损风险最高，
  「砍价免拼 → 发卡 → 确认发货」三步顺序不能错。

## 八、总体评价

**优势**

1. 架构清晰且有自动化门禁守护，不会随时间腐化
2. 测试覆盖极强（测试代码 : 生产代码 = 1.5 : 1）
3. 三种数据库 + 三平台桌面端 + 容器，部署形态完整
4. 业务规则沉淀充分（砍价顺序、MTOP 节流都写成了不可变约束）
5. **本地零依赖可跑**（SQLite + 单二进制），这在同类项目里很少见

**劣势 / 待改进**

1. 源码构建需要 Go 1.26 + Node 24，对非开发者门槛不低（官方安装包缓解了这一点）
2. Chromium 与二进制分离分发，导致自定义部署时必须显式传路径
3. `tools/smoke` 没有 Windows 分支实现，`make smoke` 在 Windows 上必然失败
4. 前端未随 Go 二进制自动检测过期（改前端必须记得重建 + 重启）

**适用判断**：如果你要长期、多账号、有交付业务的闲鱼运营，这个项目值得投入；
如果只是偶尔回个消息，它偏重。
